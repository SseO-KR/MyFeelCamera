## 어디까지 활용했는가

앱 완성과 핵심 기술 학습을 함께 목표로 삼았기 때문에, 단계마다 AI에 맡기는 일을 달리했습니다. 초기에는 코드 골격과 설명을 받아 직접 구현했고, 이후에는 기능 구현·수정·테스트 작성까지 활용했습니다. 구현을 읽고 모르는 개념을 찾아가며 학습하고, 각 제안의 대안과 적용 여부를 함께 검토했습니다.

| 영역 | AI의 역할과 실제 활용 | 직접 맡은 작업 |
| --- | --- | --- |
| 요구사항·설계 | 제품 요구 정리, 패키지·객체 책임 비교, 구현 로드맵 초안 | 원하는 촬영 경험, 우선순위, 현재 구현할 범위 설정 |
| 학습 지원 | 개념·실행 흐름 설명, 초기 코드 골격과 리뷰, 이후 구현 코드 설명 | 초기 코드 작성, 이후 구현 흐름을 따라가며 모르는 개념 학습·대안 비교 |
| 초기 프로젝트 구성 | Gradle·Manifest·Hilt/KSP 구성, 권한 요청 같은 표준 코드 작성 지원 | 학습 대상과 구성 작업 구분, 설명과 실제 빌드 결과가 다른 부분 재검토 |
| 기능 구현·수정 | 촬영 분석 이벤트 연결, 반복 오류 알림 개선과 테스트 코드 작성 | 원하는 동작 정의, 구현을 읽고 수정할 부분 제시, 대안과 적용 여부 공동 검토 |
| 검증 지원 | 빌드·정적 검사·단위 테스트, 허가된 기기 점검과 근거 정리 | 직접 실기기 검증, 테스트 대상과 허가 범위 지정, 후속 작업 판단 |
| 문서 작성 | 코드·설계·개발 기록을 읽고 README·상세 문서 작성, 링크 확인 | 독자와 전달 목적, 목차·실제 이미지·상세 페이지 구성 요청 |

이 표는 작업 원칙과 확인 가능한 사례를 정리한 것입니다. 코드 줄 수나 전체 구현 기여율은 측정하지 않았으므로 비율로 표시하지 않습니다. LUT와 초기 셰이더는 별도로 제공된 자산이며, 이 자산의 원본 제작을 개발자나 AI의 성과로 계산하지 않습니다.

## 학습 방식을 바꾼 이유

초기에는 AI의 역할을 설계를 검토하고 구현 순서를 안내하는 멘토로 정했습니다. CameraX 바인딩, Surface 공급, OES 텍스처, 셰이더 연결, LUT 업로드처럼 학습의 중심이 되는 부분은 AI가 완성본을 먼저 채우지 않고 골격과 TODO를 제시하도록 했습니다.

실제로 초기 골격 단계에서는 권한 요청 같은 표준 코드는 작성 지원을 받고, `CameraController.bind()`와 프리뷰 연결은 학습할 구현으로 남겼습니다. `bind()`의 비동기 처리 방식도 처음부터 정답처럼 고정하지 않고 API를 조사하며 결정하도록 했습니다. **(초기 의사결정 기록)**

한 단계씩 코드를 작성하면서 필요한 개념을 모두 익히려니 구현 속도가 많이 느려졌습니다. AI의 구현 능력이 발전하면서, 먼저 동작하는 결과를 만들고 그 코드를 읽으며 모르는 부분부터 학습하는 바텀업 방식을 시도했습니다. 기능 구현과 학습을 함께 진행하고, 이해가 부족한 부분은 실행 흐름과 다른 구현 방법을 질문하며 보완했습니다.

제안된 방향을 그대로 확정하지 않고 다른 방식이 있는지 확인했습니다. 구현을 보며 수정을 요청하고, 장단점과 제품에 맞는 선택을 AI와 함께 고민했습니다. 아래 사례는 그 과정에서 AI가 코드 수정과 테스트 작성까지 수행한 작업입니다. [현재 협업 지침](../../CLAUDE.md)

## 사례 1 반복 오류 알림 개선

**문제 발견:** 다국어 적용 후 코드 관리와 불필요한 화면 재구성 여부를 리뷰해 달라고 요청했습니다. AI는 오류 메시지의 리소스 ID를 알림 식별에도 사용해, 같은 오류가 연속으로 발생하면 다시 표시되지 않는 경로를 지적했습니다.

**대안 질문:** 곧바로 수정을 맡기기 전에 `StateFlow`의 문제를 어떻게 해결하는지, `SharedFlow`나 `Channel`이 더 적절하지 않은지 설명과 예시를 요청했습니다. 이 과정에서 AI의 처음 표현인 “일회성 이벤트로 분리”가 구체화됐고, 같은 내용의 재발생과 화면이 일시 중지된 동안의 대기를 처리할 방법을 비교하게 됐습니다.

**구현 요청과 AI 작업:** 설명을 확인한 뒤 권장한 방식으로 변경하도록 요청했습니다. AI는 `CameraNoticeStore`를 추가하고 ViewModel·Route의 알림 처리를 수정했으며, 관련 단위 테스트를 작성했습니다. 같은 내용이라도 발생마다 새 ID를 부여하고, 화면이 `RESUMED`일 때 `Toast.show()`를 호출한 뒤 해당 ID만 확인 처리하는 방식입니다.

**검증과 한계:** 같은 메시지의 재발행과 과거 알림의 확인 응답이 새 알림을 지우지 않는 경우를 테스트했습니다. 이후 개발자가 해당 오류 처리만 에뮬레이터로 검사하도록 별도 요청했고, 당시의 24장 한도 오류를 두 번 표시하는 결과를 확인했습니다. 계측 검사는 Activity의 키 이벤트 경로를 호출한 것이며, 에뮬레이터 창의 볼륨 버튼부터 이어지는 전체 입력 경로를 검증한 것은 아닙니다. 현재 정책에서는 24장 한도를 사용하지 않습니다.

이 방식은 ViewModel이 살아 있는 동안 가장 최근 알림 하나를 보관합니다. 모든 알림을 순서대로 전달하는 큐는 아닙니다. 또한 확인 처리는 Toast 표시 요청 직후에 이루어지므로, 사용자가 실제로 알림을 봤거나 표시가 끝났음을 보장하지 않습니다.

| 역할 | 이 사례에서 한 일 |
| --- | --- |
| 직접 수행 | 반복 알림에 필요한 동작 정의 → StateFlow·SharedFlow·Channel 대안 비교 → 구현·수정 방향 검토 → 테스트 범위 결정 |
| AI | 문제 경로 분석 → 대안 설명 → 코드 수정·테스트 작성 → 실행 결과와 한계 보고 |

확인 가능한 구현: [CameraNoticeStore](../../app/src/main/java/com/newfeelcamera/ui/camera/CameraNoticeStore.kt) · [단위 테스트](../../app/src/test/java/com/newfeelcamera/ui/camera/CameraNoticeStoreTest.kt)

## 사례 2 촬영 분석의 계획과 구현

**목적 설정:** 필름별 촬영 횟수, 가로·세로 사진, 플래시 사용을 파악하고 싶다는 요구에서 시작했습니다. 구현 전에 계획과 문서를 먼저 작성하도록 요청했습니다.

**설계 구체화:** AI와 함께 셔터 시도가 아닌 사진 저장 성공을 집계 기준으로 정리했습니다. 저장된 사진의 방향을 화면 방향으로 추정하지 않고 최종 이미지 크기에서 구분하며, 필름·플래시 설정은 셔터 시점의 값으로 기록하는 계획을 세웠습니다.

**구현 요청과 AI 작업:** 개발 진행을 요청한 뒤 AI가 `CaptureAnalytics`, Firebase/no-op 구현, 촬영 결과 모델과 이벤트 연결, 사진 방향 분류 테스트를 작성했습니다. GA4의 맞춤 측정기준 등록과 관련 문서 갱신도 지원했습니다. 이후 이벤트 코드와 콘솔의 측정기준이 각각 어떤 역할인지 추가 설명을 요청해 연결 구조를 확인했습니다.

**결과 해석:** 당시 단위 테스트와 Firebase 포함·제외 빌드 결과를 확인했지만, 기기에서 보낸 이벤트가 콘솔에 도착하는지는 미검증으로 남겼습니다. 기능 구현 완료와 실제 데이터 수신은 별도 완료 기준으로 다뤘습니다.

무료·무제한 출시를 결정한 2026-10-08에는 동의·고지 준비를 위해 Firebase SDK를 기본 빌드에서 제외했습니다. 이후 2026-10-09에 Release 기본 포함으로 정책을 바꾸고, 첫 실행에서 Analytics·Crashlytics를 각각 선택하며 설정에서 변경하는 흐름을 연결했습니다. 현재 코드는 선택에 따라 수집하고, `photo_saved`의 콘솔 수신 확인은 별도 과제로 남겨 두었습니다.

## 사례 3 AI의 설명을 빌드 결과로 수정

초기 Gradle 구성에서 AI가 추정한 라이브러리 버전과 실제 환경이 맞지 않았습니다. 실제 CLI로 확인하도록 요청한 뒤 패키지 저장소의 버전 정보와 빌드 오류를 기준으로 구성을 수정했습니다. **(초기 환경 구성 기록)**

이 과정에서 Kotlin 내장 방식에 관한 요약 설명을 따라 Compose Compiler 플러그인을 제거했다가, 실제 빌드가 해당 플러그인을 요구하는 오류를 만났습니다. 설명을 다시 검토하고 플러그인 구성을 바로잡은 뒤 빌드 성공을 확인했습니다.

이 경험 이후에는 버전이나 플랫폼 동작을 AI의 설명만으로 확정하지 않고, 현재 프로젝트의 도구 출력과 공식 근거를 함께 확인하는 기준을 적용했습니다. 추정이나 미확인 설명은 검증할 항목으로 남겼습니다.

현재 구성: [플러그인·의존성](../../app/build.gradle.kts) · [버전 카탈로그](../../gradle/libs.versions.toml). 이 사례는 당시 문제 해결 기록이며 해당 버전이 현재의 최신 버전이라는 설명은 아닙니다.

## 협업 과정에서 유지한 기준

1. **문제와 범위를 먼저 전달했습니다.** 학습 설명, 코드 리뷰, 실제 수정, 기기 테스트를 구분해 요청했습니다. 에뮬레이터 점검은 별도 허가 범위로 관리했습니다.
2. **대안을 질문하고 적용을 결정했습니다.** 오류 알림의 전달 방식이나 SurfaceProvider 소유권처럼 처음 제시된 결론의 전제를 다시 확인했습니다. [소유권 재검토 사례](preview-lifecycle.md#surfaceprovider-소유권을-다시-판단한-이유)
3. **AI의 실행 지원을 검증 근거에 연결했습니다.** 코드 수정과 함께 관련 테스트·빌드·로그를 확인하고, 실제 기기에서 확인하지 못한 부분은 남겨두었습니다.
4. **제품 판단과 구현 가능성을 나눠 봤습니다.** 준비하던 결제는 세무·운영 부담을 고려해 보류했고, 분석은 수집 동의를 연결한 뒤 Release에 포함했습니다. [제품 범위 결정](product-and-development.md#초기-출시-범위를-바꾼-이유)
5. **AI가 작성한 결과물도 활용 범위에 포함했습니다.** 기능 코드·테스트뿐 아니라 README와 상세 문서에도 AI의 작성 지원을 받았습니다. README의 WARM·DUSK 소개 이미지는 에뮬레이터 UI에 직접 촬영한 사진을 합성했습니다.

실기기 검증은 Galaxy S10(Android 12)과 Galaxy S25+(Android 16)에서 직접 진행했습니다. [실기기 확인 환경](validation.md#실기기-확인-환경)
